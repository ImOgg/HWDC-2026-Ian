# 實作與驗證方法

## 判讀任務
先確認是新增、缺陷修復、重構或既有行為修改。讀實際 baseline，不假設專案是空白或功能已存在。
建立精簡工作對照：task → 受影響層／契約 → 適用規則編號 → 接受情境／回歸驗證。不要將此對照當成另外一份業務規格。
動手前寫下本次假設（CORE-01）；Spec 有多種解讀或缺關鍵資訊時回報 BLOCKED，不自行決定。每項 task 先確定成功條件與驗證方式（CORE-04）：缺陷修復先寫重現測試，重構前後既有測試都要通過。

## 依規範實作
- 依 CORE-02、CORE-03：只寫完成 task 所需的程式，不加未要求的功能、設定或抽象；只改 task 或 finding 需要的地方，不順手調整相鄰程式、註解或格式。發現無關的死碼在回報中提出，不直接刪除；本次改動造成不再使用的程式要一併移除。
- 依 ARCH 規則放置責任並維持相依方向；資料存取使用介面，具體實作留在 Infrastructure。
- 依 NAME／CODE 規則處理名稱、錯誤、非同步與生命週期；延續現有風格，避免無關改動。建置會以 .editorconfig 檢查命名、以 TreatWarningsAsErrors 擋下警告、以架構測試檢查層級相依，依錯誤訊息修正程式，不修改這些設定或測試。
- 依 SEC 規則處理本次實際輸入、輸出、授權、儲存與外部操作，不假設特定部署或資料庫。
- 依 TEST 規則選擇單元／整合測試，確認實質 assertions。缺陷修復先建立重現證據，重構核對既有行為；新功能依 Spec 寫接受情境測試。

## 執行驗證
讀 docs/project-context.md 取得 solution、測試專案與驗證入口，保持既有命名與路徑。執行 `pwsh -NoProfile -File eng/verify.ps1`，它依序執行 dotnet restore、build、test，任一步失敗即以 exit 1 結束。
MVC 整合測試依專案架構使用 WebApplicationFactory 等工具，保留真實安全機制；入口不可見時以最小必要改動支援測試。
檢查當次 build 輸出、每個測試專案的執行摘要、TRX 與測試內容。不得以「命令 exit 0」替代測試已執行的證據；零測試、失敗、未執行或必要情境被略過都不能視為完成。
新增測試專案時，同步更新 eng/verify.ps1 的測試專案清單與 docs/project-context.md，並列入本次修改檔案。
驗證後只勾選實際完成的 tasks，回覆命令、結果與限制。任何修正都須重新驗證，由主 Agent 重新安排兩道審查。
