# 共通行為準則

所有角色都適用：主 Agent、Coding、Code Review、Fortify preverify，以及使用 AI 工具的人。其他規範定義「程式要做到什麼程度」，這份定義「工作時的行為」。

- **CORE-01 必要｜先想清楚再寫**：開始前寫出本次工作的假設。需求或 Spec 有多種解讀時，列出各種解讀並詢問，不自行挑一種；發現更簡單的做法時提出；不清楚的地方要指名說明，缺少關鍵資訊時回報 BLOCKED，不靠猜測補齊。
- **CORE-02 必要｜簡單優先**：只寫完成本次 Spec 與 tasks 所需的程式。不加入未要求的功能、只用一次的抽象、未要求的可設定性，也不替不可能發生的情境寫錯誤處理。判斷標準：資深工程師看了會不會覺得過度複雜。
- **CORE-03 必要｜精準修改**：只改本次 task 或 finding 需要的地方。不順手改相鄰的程式、註解或格式，不重構可正常運作的程式，沿用既有風格。看到與本次無關的死碼，在回報中提出，不直接刪除；自己這次改動造成不再使用的 using、變數或方法，要一併移除。判斷標準：每一行變更都能對回本次的 task 或 finding。
- **CORE-04 必要｜以可驗證的目標推進**：先把任務轉成可驗證的成功條件再動手。修缺陷先寫能重現問題的測試再讓它通過；重構前後既有測試都要通過；多步驟任務先列簡短計畫與每一步的驗證方式。驗證沒有通過，不宣告完成。

## 由誰檢查

| 規則    | 檢查方式                                                                                                                            |
| ------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| CORE-01 | 主 Agent 在 OpenSpec 討論時列出歧義並詢問；Coding 遇到 Spec 歧義回報 BLOCKED；Review 發現程式的行為來自未經確認的假設時提出 finding |
| CORE-02 | Code Review 對照 Spec 與 tasks：未要求的功能、設定或抽象為阻擋問題；寫法還能再簡化但不影響需求時，標為非阻擋建議                    |
| CORE-03 | Code Review 以 `git diff` 對照 tasks 與 findings，找不到對應依據的變更為阻擋問題                                                    |
| CORE-04 | `eng/verify.ps1` 與 TEST 規則；Spec 的接受情境要有對應測試                                                                          |

這四條與 ARCH-07（不為了湊 DDD 名詞引入無用途的物件）、TEST-03（修缺陷先建立重現測試）方向一致；條文重疊時兩邊都適用。
