# 測試審查方法

標準來源：docs/team-rules/testing.md。具體期望來源：本次 Spec 與受影響的既有契約。

1. 對照接受情境 → 實際測試符號 → 關鍵 assertions → 本次執行結果。找到沒有驗證的情境，或測試與實作共同誤解規格的情況。
2. 核對測試是否放在適當責任層、替身是否掩蓋真正要驗證的行為、整合測試是否真的穿過需檢查的管線。
3. 核對成功／拒絕／邊界及受影響回歸；並行、權限等情境是否必要，由 Spec／design 與實際風險判斷。
4. 檢查測試隔離、資料與時間控制、assertion 強度，以及被刪除、略過或弱化的既有測試。
5. 閱讀本次 log/TRX 的測試、失敗與未執行結果，確認對應受檢內容。零測試、舊報告、空 assertion 或只看方法名稱均不充分。

測試全綠後仍有接受條件缺口，應依 TEST／Spec 提出 finding。不要預先要求某個業務方法、HTTP 狀態或固定測試名稱。
